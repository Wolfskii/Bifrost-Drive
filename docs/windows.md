# Windows

Windows 11 22H2+ on NTFS is the first-release target. CFAPI lets Explorer display sync-root placeholders and hydrate files on demand. A separate WinFsp adapter provides genuine network-location or local drive-letter mounts with provider-backed filesystem operations. A connection uses its selected drive letter when configured; otherwise it uses a CFAPI sync folder, and the desktop does not register both presentations at once.

Closing the main window hides it to the persistent tray; only the tray Quit command exits Bifrost and releases mounted drives. Left-clicking the tray icon restores and focuses the main window, while right-clicking opens the context menu. Bifrost is single-instance, so launching it again reveals the existing tray-owned window instead of creating a competing mount owner. Drive presentation and icon choices are persisted per connection and can be changed from the full-page Edit connection view. The icon picker renders the complete Windows `SHELL32.dll` icon catalog plus named stock icons and accepts custom images or native icon sources. Network labels and icons use Explorer's MountPoints2 metadata so generated WinFsp server identities remain internal. Every normal uninstall stops the tray process, unregisters legacy CFAPI roots, and removes Bifrost DriveIcons and MountPoints2 metadata. Selecting full local-data deletion additionally removes `%USERPROFILE%\Bifrost Drive`, with locked leftovers scheduled for deletion after reboot.

Google Drive and Immich use local-drive presentation so Explorer shows only the configured connection name, without WinFsp's generated UNC server identity. Existing connections adopt this presentation on their next remount and stale Bifrost network metadata is removed.

Current status: Tauri desktop shell, Windows GUI-subsystem builds, per-machine Program Files installation, native start-on-boot registration, CFAPI registration, placeholder transfer, provider-backed hydration, local close/delete/rename routing, writable WinFsp callbacks, persisted drive selection, per-connection startup remount and live mount/unmount controls, provider capacity reporting where available, clean Explorer drive labels, hidden attributes for remote dotfiles, durable application history, notifications, updater configuration, and signed-package workflow support are implemented. WinFsp fetches provider capacity at mount, refreshes it every minute, and prompts a throttled refresh when Explorer requests volume information. Directory metadata remains cached for five seconds, and per-handle read-ahead grows from 1 MiB to 32 MiB for sequential transfers; completed chunks are delivered to Explorer immediately instead of waiting for the full range. SFTP range reads keep 16 ordered 1 MiB chunks in flight over a 64 MiB SSH channel window and prefer hardware-accelerated AES-GCM when supported. SSH keepalives prevent idle network timeouts, and cached SFTP sessions are validated after inactivity and reconnected when stale. Read-ahead is capped to the advertised remote size, and incomplete SFTP ranges fail instead of being reported as EOF. Incremental delivery keeps Explorer copy progress smooth while retaining parallel I/O. Mutations invalidate metadata immediately. Real drive acceptance covers read, write, create, rename, delete, directory operations, unmount, cache warming, and read-ahead against an in-memory provider. Explorer acceptance and throughput measurement against each live provider remain required. New SFTP connections enable trust-on-first-use by default while saved connections preserve their explicit setting. CFAPI folders are not aliased to drive letters.

If a terminated or uninstalled development build leaves an Explorer drive tile behind, run `task cleanup:windows-drives` from the repository root. The interactive menu lists only stale entries with Bifrost's generated WinFsp identity and an inactive Bifrost owner PID; generic Explorer drive history is never shown. Cleanup repeats the shell refresh and Explorer restart needed to remove a persistent tile. The operating-system drive is hard-blocked, and current non-Bifrost drives and unrelated network mappings are rejected.

Windows development requires Visual Studio Build Tools, the Windows SDK, WebView2, and a clean test account or VM. Building the native WinFsp feature additionally requires WinFsp 2.1 or later, installed from an elevated terminal with `choco install winfsp -y`. End users do not install this prerequisite separately: the Bifrost NSIS installer bundles the official unmodified WinFsp 2.1.25156 MSI, verifies its pinned checksum during packaging, and installs it silently when needed. Bifrost does not remove WinFsp during uninstall because other applications may share it. Selecting local-data deletion in the uninstaller also removes `%USERPROFILE%\Bifrost Drive`; ordinary uninstall and in-place updates preserve it.
