# Windows

Windows 11 22H2+ on NTFS is the first-release target. CFAPI lets Explorer display sync-root placeholders and hydrate files on demand. A separate WinFsp adapter provides genuine network-location or local drive-letter mounts with provider-backed filesystem operations. A connection uses its selected drive letter when configured; otherwise it uses a CFAPI sync folder, and the desktop does not register both presentations at once.

Closing the main window hides it to the persistent tray; only the tray Quit command exits Bifrost and releases mounted drives. Left-clicking the tray icon restores and focuses the main window, while right-clicking opens the context menu. Bifrost is single-instance, so launching it again reveals the existing tray-owned window instead of creating a competing mount owner. Drive presentation and icon choices are persisted per connection and can be changed from the full-page Edit connection view. The icon picker renders the complete Windows `SHELL32.dll` icon catalog plus named stock icons and accepts custom images or native icon sources. Network labels and icons use Explorer's MountPoints2 metadata so generated WinFsp server identities remain internal. Every normal uninstall stops the tray process, unregisters legacy CFAPI roots, and removes Bifrost DriveIcons and MountPoints2 metadata. Selecting full local-data deletion additionally removes `%USERPROFILE%\Bifrost Drive`, with locked leftovers scheduled for deletion after reboot.

Google Drive and Immich use local-drive presentation so Explorer shows only the configured connection name, without WinFsp's generated UNC server identity. Existing connections adopt this presentation on their next remount and stale Bifrost network metadata is removed.

Current status: Tauri desktop shell, Windows GUI-subsystem builds, per-machine Program Files installation, native start-on-boot registration, CFAPI registration, placeholder transfer, provider-backed hydration, local close/delete/rename routing, writable WinFsp callbacks, persisted drive selection, per-connection startup remount and live mount/unmount controls, provider capacity reporting where available, clean Explorer drive labels, hidden attributes for remote dotfiles, durable application history, notifications, updater configuration, and signed-package workflow support are implemented. WinFsp fetches provider capacity at mount, refreshes it every minute, and prompts a throttled refresh when Explorer requests volume information. Directory metadata is cached for five seconds, or five minutes while the provider's change polling (every 15 seconds) is healthy; each reported change invalidates only the affected paths, and any polling failure drops back to the five-second lifetime. The first read on a handle fetches 1 MiB; a sequential continuation opens one streaming range to the end of the file that stays at most 32 MiB ahead of the reader and keeps 4 MiB behind it for slightly out-of-order reads, so large copies no longer pause between chunk requests. Far forward seeks start a new range, an interrupted stream resumes at the gap, and closing the handle stops the transfer. Completed chunks are delivered to Explorer immediately instead of waiting for the full range. SFTP range reads keep 16 ordered 1 MiB chunks in flight over a 64 MiB SSH channel window and prefer hardware-accelerated AES-GCM when supported. SSH keepalives prevent idle network timeouts, and cached SFTP sessions are validated after inactivity and reconnected when stale. Read-ahead is capped to the advertised remote size, and incomplete SFTP ranges fail instead of being reported as EOF. Incremental delivery keeps Explorer copy progress smooth while retaining parallel I/O. Mutations invalidate cached metadata for the changed path, its subtree, and its parent listing immediately; unrelated directory listings stay cached. Real drive acceptance covers read, write, create, rename, delete, directory operations, unmount, cache warming, and read-ahead against an in-memory provider. Explorer acceptance and throughput measurement against each live provider remain required. New SFTP connections enable trust-on-first-use by default while saved connections preserve their explicit setting. CFAPI folders are not aliased to drive letters.

If a terminated or uninstalled development build leaves an Explorer drive tile behind, run `task cleanup:windows-drives` from the repository root. The interactive menu lists only stale entries with Bifrost's generated WinFsp identity and an inactive Bifrost owner PID; generic Explorer drive history is never shown. Cleanup repeats the shell refresh and Explorer restart needed to remove a persistent tile. The operating-system drive is hard-blocked, and current non-Bifrost drives and unrelated network mappings are rejected.

Windows development requires Visual Studio Build Tools, the Windows SDK, WebView2, and a clean test account or VM. Building the native WinFsp feature additionally requires WinFsp 2.1 or later, installed from an elevated terminal with `choco install winfsp -y`. End users do not install this prerequisite separately: the Bifrost NSIS installer bundles the official unmodified WinFsp 2.1.25156 MSI, verifies its pinned checksum during packaging, and installs it silently when needed. Bifrost does not remove WinFsp during uninstall because other applications may share it. Selecting local-data deletion in the uninstaller also removes `%USERPROFILE%\Bifrost Drive`; ordinary uninstall and in-place updates preserve it.

## Explorer transfer menu

Windows offers no supported way to replace Explorer's own copy dialog, so Bifrost Drive adds menu items instead (`platforms/windows/shell`, a COM shell extension loaded by Explorer): **Delete with Bifrost Drive** on items that are on a Bifrost drive (after a confirmation; there is no recycle bin on a server, and a whole drive is never offered), **Copy here / Move here with Bifrost Drive** on a right-drag, and **Paste with Bifrost Drive** when right-clicking a folder, a drive, or empty folder space with files on the clipboard (a cut pastes as a move). Paste is offered on every drive, so large local copies can use the transfer window too; the right-drag items appear only when the source or the target is on a Bifrost drive (recognised by its file system name `Bifrost`), so ordinary drags never see them. Ctrl+V and left-drag stay Explorer's own, and on Windows 11 "Paste with Bifrost Drive" sits under "Show more options" (a top-level entry would need a packaged app identity).

The extension does no transfer work. It writes a JSON request to `%LOCALAPPDATA%\com.bifrost.drive\transfer-requests` and starts `bifrost-drive.exe --transfer-request <file>`; the running app accepts request files only from that folder, resolves each path to a local folder or a mounted drive, and runs it in the transfer window (bounded parallelism, byte-level progress, pause and cancel, name-clash prompts, retries). A move deletes a source only after its destination was written and, where the provider reports sizes, verified. Settings has a switch ("Show Bifrost Drive transfer options in Explorer menus", on by default); it is published to `HKCU\Software\Bifrost Drive\ExplorerTransferMenu`, which the extension reads on every menu build, so it takes effect immediately.

The transfer window is wide and short, like Explorer's own copy dialog. When every transfer has finished cleanly it closes itself after about a second and a half, and the next transfer opens a fresh window; it stays open while anything is running, waiting for an answer to a name clash, or has problems. Every transfer is also written to a log (SQLite table `transfer_history`: the selected paths, the destination, counts, state and the first failures, never file contents), shown on the app's **Transfers** page with live progress for running transfers. The log keeps the latest 500 entries, "Clear finished" empties it, and a transfer that was still running when the app stopped is marked "Interrupted" on the next start.

The installer registers the extension per machine (`HKLM\Software\Classes`) and records the app path in `HKLM\Software\Bifrost Drive\ExePath`; an update renames a loaded DLL aside because Explorer keeps it locked, and uninstall removes the keys. For development use `task shell:register`, `task shell:restart-explorer` after a rebuild, and `task shell:unregister`. Limitations: UNC paths (`\bifrost-1\...`) are not recognised, only drive letters; case-insensitive name clashes against a case-sensitive server are not detected; Explorer acceptance on a real drive and the signed release installer still need a Windows VM run.
